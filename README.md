# OBSCURA RS-1

A scroll-driven product page. A numbered image sequence is painted to a fixed
full-screen canvas behind the content, and scroll position across the whole
document maps to the frame index.

Next.js (App Router) · TypeScript · Tailwind v4 · GSAP ScrollTrigger · Lenis.
Deploys to Vercel with no configuration.

```bash
npm install
npm run dev          # http://localhost:3000
npm run build
```

## The frames are placeholders

`public/frames` currently holds a synthetic rotating lens element, generated by
`scripts/build-frames.mjs`. It is there so the sequence machinery can be built
and measured against real files at the real spec — 1600px wide WebP, quality
80. **It is not the product.** Swap it for real photography as below; no
component changes are needed.

Art direction reference lives in `/reference`.

## Swapping in new frames

The frame count is read from the folder on the server at build time
(`app/page.tsx`), so nothing needs updating when the number changes.

From a turntable video:

```bash
node scripts/build-frames.mjs --from ~/shoot/turntable.mp4 --count 180
```

From a folder of stills (PNG, JPG or WebP, sorted naturally by filename):

```bash
node scripts/build-frames.mjs --from ~/shoot/frames/
```

To regenerate the placeholders, or change their length:

```bash
node scripts/build-frames.mjs --placeholder --count 180   # public/frames
node scripts/build-frames.mjs --worn --count 96           # public/worn
node scripts/build-frames.mjs --hero                      # public/hero.jpg
```

Either way the output is `public/frames/frame-0001.webp …`, resized to 1600px
and encoded at quality 80. The script wipes the folder first, so a shorter
sequence never leaves stale frames behind.

### What makes a good source sequence

- Landscape, product centred, on black or transparent — the canvas sits on a
  near-black page and letterboxes invisibly.
- The placeholder is a wrapped sport shield: tall lens, near-straight brow bar,
  squared outer corners, bottom sweeping up toward the temples.
- The placeholder sweeps a ±58° arc rather than a full 360°. A full turn
  passes edge-on twice, where the projected width changes fastest and the
  motion visibly snaps. If you shoot a real 360, keep the turn slow through
  those two points or shoot an arc instead.
- 120–200 frames. Fewer stutters under a fast flick; more costs load time for
  motion nobody can see.
- Keep the product inside the safe box described below.

## How the canvas works

`lib/frameGeometry.ts` holds the numbers the preloader and the canvas must
agree on.

**Dimming.** The dim ranges overlap by design — one section's end sits past
the next one's start. Triggers therefore only record whether they are active,
and a single tween animates the strongest dim currently asked for, with
`overwrite: true`. Letting each trigger animate opacity itself makes two
tweens race for the same property, and the loser silently wins about half the
time. See `DIM_OVER` in `components/FrameCanvas.tsx`.

**Fitting.** Rather than cover-fitting the whole frame, which would crop the
product on a narrow screen, the frame is scaled so a 1900 × 900 *safe box*
always fits. Empty margin crops away, the product never does, and it occupies
the same fraction of the viewport on a phone as on a desktop. If your frames
have the product filling more or less of the frame, adjust `PRODUCT_W` and
`PRODUCT_H`.

**Decoding.** An `ImageBitmap` never hitches while scrolling, but it is pinned
memory that the browser cannot evict. A phone paints these a few hundred pixels
wide, so the whole sequence fits inside a 256 MB budget and bitmaps win. A
desktop wants them near source size, where 180 frames would run to about a
gigabyte — past the budget the frames are loaded as ordinary images instead and
Chrome's own cache decides what stays decoded. See `lib/frames.tsx`.

**Painting.** Scroll writes a fractional target index; GSAP's ticker — the
page's single `requestAnimationFrame` loop — reads it and draws the current
frame with the next one laid over it at the fraction's alpha. That blend reads
as motion blur and removes the step between frames, whatever the sequence.
Canvases skip painting entirely while they are faded out or off screen. Fit is
computed on resize and cached, so the draw loop never reads layout. Device
pixel ratio is capped at 2.

**Preloading.** Every frame is decoded before the page is revealed, eight at a
time. Frame one is fetched first and painted immediately, so nothing flashes.

## The worn sequence

`public/worn` holds a second sequence — a rim-lit profile with the product
lifting off the face — driven by `components/WornSequence.tsx` and scrubbed
against its own section rather than the whole page. It cover-fits, because the
head is centred and cropping the sides keeps it large on a phone.

It is a silhouette on purpose. A synthetic photograph of a model wearing a
product reads as a fake; a lit outline reads as art direction. Replace it with
real footage the moment you have some:

```bash
node scripts/build-frames.mjs --from ~/shoot/taking-them-off.mp4 --count 96
mv public/frames public/worn     # or point --from at the worn folder directly
```

`components/sections/Worn.tsx` counts the folder on the server and renders
nothing at all if it is empty, so deleting `public/worn` removes the section
cleanly.

## Sections

`app/page.tsx` composes them in order: hero, three feature statements,
specification, material story, the worn sequence, gallery, call to action,
footer. Each block of
text is wrapped in `<Reveal>`, which scrubs opacity, blur and a small
translate against its own scroll range so text focuses in as it arrives and
defocuses as it leaves.

The canvas steps back behind the sections listed in `DIM_OVER`
(`components/FrameCanvas.tsx`) so long-form text stays readable.

## Design tokens

In `app/globals.css` under `@theme`. Near-black `--color-ink`, off-white
`--color-bone`, and a single accent `--color-accent` (`#c8ff3c`) pulled from
the lens. Display type is Archivo with its width axis pushed to 112; labels and
specs are JetBrains Mono at 11px, tracked out.

## Accessibility and motion

`prefers-reduced-motion: reduce` disables Lenis and all scrubbing, paints one
static three-quarter frame, and renders every text block at rest with no blur
or transform. Verified in Chrome with the media feature emulated.

## Measured

Traced in headful Chrome on an M-series Retina Mac, 5s of synthetic wheel
scrolling, `DrawFrame` intervals and main-thread totals from
`disabled-by-default-devtools.timeline.frame`, median of 3 runs per variant.

| variant | Commit | presented | dropped |
|---|---|---|---|
| baseline | 1159 ms | 324 | 1 |
| DPR capped at 1 | 1147 ms | 325 | 1 |
| conditional crossfade | 1165 ms | 324 | 0 |
| noise tile, no blend mode | 1090 ms | 325 | 1 |
| nav blend removed | 1078 ms | 324 | 1 |
| blur 4px, `filter: none` at rest | 1136 ms | 325 | 1 |

Repeated runs of a *single* unchanged build gave Commit of 941, 1104, 1147 and
1175 ms, so the whole table sits inside run-to-run noise. Every variant,
baseline included, presented 324–326 frames in 5 seconds and dropped 0–1.

The honest reading: on this machine the page already runs at 60fps, and none
of the optimisations below can be shown to have changed that. They are kept
because they remove real work — a quarter of the canvas pixels, two
compositing groups, and every filter layer at rest — not because a measurement
credits them.

**Commit is flat at ~1.1s across every variant**, which rules out the blend
modes, the filters and the second canvas draw. Roughly 3.5 ms per frame, it
tracks the canvas texture upload: a full-screen canvas whose contents change
every frame has to be re-uploaded every frame. That is inherent to a
scroll-driven sequence. The lever that would move it is a backing store
smaller than the CSS size, letting the compositor scale it up.

## Scroll feel versus frame rate

If scrolling feels wrong while the frame rate is fine, the cause is lag, not
jank. Two knobs:

- `duration` in `lib/SmoothScroll.tsx` (1.1) — how far Lenis trails the input.
- `scrub` in `components/FrameCanvas.tsx` (0.6) — how far the frame index
  trails the scroll. These compound.

And one trade-off worth knowing. `BLEND_ABOVE` in `components/FrameCanvas.tsx`
gates the crossfade on scroll speed. At one frame per ~54px of scroll:

| scroll speed | frames per tick | crossfade |
|---|---|---|
| 400 px/s | 0.12 | off — frames snap |
| 800 px/s | 0.25 | off — frames snap |
| 1600 px/s | 0.49 | on |

Stepping is most visible at *low* speed, which is exactly where this gate turns
the crossfade off. Since the second draw was measured to cost nothing, setting
`BLEND_ABOVE` to about `0.01` keeps the blend everywhere except at a standstill.

## Known gaps

- The footer signup is local state only. Wire it to a list provider before it
  ships.
- Gallery stills are pulled from the loaded sequence rather than being separate
  photography. Replace the four paths in `components/sections/Gallery.tsx`.
- Frames are decoded once for the viewport size at load. Dragging a window from
  phone width to a large display without reloading leaves them slightly soft.
- `lib/gsap.ts` puts `gsap` and `ScrollTrigger` on `window` in development for
  instrumentation. Stripped from production builds.
- The worn silhouette is deliberately androgynous and hairstyle-neutral. If the
  brand wants a specific person, that needs real photography.
